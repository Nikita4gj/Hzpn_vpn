# HZPN - **H**ardened **Z**ero-trust **P**ersonal **N**etwork

Учебная реализация VPN, работающего на сетевом уровне (L3): весь IP-трафик клиента перехватывается через TUN-интерфейс, инкапсулируется и передаётся на сервер, который распаковывает пакеты и выпускает их в сеть от своего имени.

Это не HTTP/SOCKS-прокси прикладного уровня — туннелируется любой IP-трафик независимо от протокола поверх него.

> **Статус:** ранняя разработка. Рабочей сборки пока нет.

## Как это устроено

```
[приложение] → [tun0] → [hzpn_client] → сеть → [hzpn_server] → [tun0] → интернет
```

1. Клиент создаёт виртуальный интерфейс `tun0` и прописывает маршруты так, чтобы трафик уходил в него.
2. Ядро отдаёт клиенту сырые IP-пакеты через файловый дескриптор TUN.
3. Клиент оборачивает пакет в кадр собственного протокола и отправляет серверу.
4. Сервер извлекает пакет, отправляет его в реальную сеть, ответ проделывает обратный путь.

## Компоненты

| Компонент     | Назначение                                                           |
| ------------- | -------------------------------------------------------------------- |
| `hzpn_client` | Создаёт TUN-интерфейс, настраивает маршруты, гоняет пакеты к серверу |
| `hzpn_server` | Принимает соединения, маршрутизирует трафик клиентов наружу, NAT     |
| `hzpn_core`   | Формат кадра, сериализация, криптография, общие утилиты              |

## Требования

- Linux с поддержкой `/dev/net/tun`
- C++20, CMake 3.25+
- Компилятор GCC 12+ или Clang 15+
- Ninja
- Для отчёта о покрытии: `gcovr`

## Сборка

```bash
cmake --preset default
cmake --build --preset debug
ctest --preset debug
```

Настройка выполняется один раз, дальше меняется только пресет сборки.
Все конфигурации живут в одном каталоге `build`, бинарники попадают в
`build/bin/<конфигурация>`, библиотеки в `build/lib/<конфигурация>`.

| Пресет сборки | Что даёт |
| --- | --- |
| `debug` | `-g3 -O0`, полный набор предупреждений |
| `release` | `-O2 -DNDEBUG` и межпроцедурная оптимизация |
| `asan` | санитайзеры адресов и неопределённого поведения |
| `coverage` | инструментация для отчёта о покрытии |

Предупреждения считаются ошибками только в пресете `ci`, который использует CI. Локально сборка на предупреждении не падает.

### Сборка без пресетов

Пресеты это только записанные команды, проект собирается и напрямую. При
обычном генераторе конфигурация выбирается на этапе настройки, поэтому под каждую нужен свой каталог:

```bash
cmake -S . -B build-debug -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build-debug -j
ctest --test-dir build-debug
```

Доступные значения `CMAKE_BUILD_TYPE` те же: `Debug`, `Release`, `Asan`,
`Coverage`. Раскладка артефактов при этом не меняется: 
`<каталог сборки>/bin/<конфигурация>` и `<каталог сборки>/lib/<конфигурация>`.

Генератор не обязан быть Ninja. Без флага `-G` на Linux берётся
`Unix Makefiles`, и проект собирается им без изменений. Ninja выбран по
умолчанию в пресетах из-за более быстрой пересборки. Генератор запоминается каталогом сборки: сменить его можно, только удалив каталог.

Отчёт о покрытии:

```bash
cmake --build --preset coverage
ctest --preset coverage
gcovr --root . --filter src/ --filter include/ --html-details build/coverage/index.html
```

## Запуск

> TODO: появится вместе с первой рабочей версией.

Оба бинарника поднимают TUN-интерфейс и правят таблицу маршрутизации, поэтому требуют capability `CAP_NET_ADMIN`. Запуск из-под `sudo` работает, но выдаёт процессу заметно больше прав, чем нужно. Предпочтительный вариант — выдать capability конкретному бинарнику один раз после сборки:

```bash
sudo setcap cap_net_admin+ep build/bin/Debug/hzpn_client
```

В примере взята конфигурация `Debug`. Для другой конфигурации меняется только 3подкаталог, например `build/bin/Asan/hzpn_client`.

Capability привязана к файлу, поэтому после каждой пересборки бинарника её нужно выдавать заново.
