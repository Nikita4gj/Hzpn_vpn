# ADR 0001. Транспорт для туннеля: TCP или UDP

- **Статус:** принято, первая итерация на TCP
- **Дата:** 2026-09-13

## Контекст

Туннелю нужен транспорт между клиентом и сервером. Рассматривались TCP, UDP и QUIC.

Внутри туннеля идёт пользовательский трафик, и это в подавляющем большинстве TCP-соединения со своими таймерами, повторными передачами и контролем перегрузки. Если внешним транспортом тоже сделать TCP, получается TCP внутри TCP — два независимых механизма надёжности поверх одного канала.

Пока сеть не теряет пакеты, такая конструкция работает. При потерях она
деградирует нелинейно:

1. Внешний TCP теряет сегмент и придерживает уже доставленные данные до повторной передачи — это head-of-line blocking.
2. Внутреннее TCP-соединение видит только задержку, срабатывает его собственный таймер, и оно ретранслирует пакет, который на самом деле не потерян, а лежит в буфере внешнего соединения.
3. Ретрансмиты внутреннего соединения добавляют трафик во внешнее, которое уже борется с перегрузкой. Оно сужает окно и растягивает таймауты.
4. Внутреннее соединение от этого ретранслирует ещё агрессивнее.

Классическое описание эффекта — Olaf Titz, «Why TCP Over TCP Is A Bad Idea»
(<https://sites.inka.de/bigred/devel/tcp-tcp.html>).

UDP этой проблемы лишён: он не гарантирует доставку и не имеет собственного контроля перегрузки, поэтому надёжностью занимается ровно один уровень — внутренний. Потеря пакета в туннеле выглядит для пользовательского соединения как обычная потеря в сети, на которую его TCP и рассчитан. По этой причине все боевые VPN (WireGuard, OpenVPN в режиме по умолчанию, IPsec) используют UDP.

## Решение

Первая итерация делается на TCP. Причина не техническая, а учебная: потоковый сокет снимает на старте вопросы обнаружения клиентов, разбора границ кадров и повторных передач, что позволяет быстрее получить работающий сквозной путь пакета от `tun0` до `tun0`.

Транспорт изолируется за интерфейсом, чтобы замена не затрагивала остальной код.

Целевой транспорт — UDP. TCP остаётся как запасной режим для сетей, где UDP режется.

## Последствия

- Ранние замеры скорости на TCP-транспорте не показательны: они верны только для сети без потерь и не переносятся на UDP-версию.
- Формат кадра обязан содержать явную длину: в UDP границы даёт датаграмма, в TCP их нет, и на этом ломаются реализации, читающие поток «как получится».
- Переход на UDP потребует собственного механизма установления сессии, keepalive и обнаружения разрыва — всё то, что TCP давал бесплатно.
- Перед сдачей стоит снять сравнительные замеры обоих транспортов при искусственных потерях (`tc qdisc add dev ... netem loss 5%`). Это готовый материал для защиты.
